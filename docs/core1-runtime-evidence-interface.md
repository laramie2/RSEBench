# Core-1 N3/N4 Runtime Evidence Interface

## Release contract

N3 and N4 are a hybrid benchmark component:

- the task split, operator, selector, seed, mutation budget, protected fields,
  and failure policy are fixed release artifacts;
- the native trajectory and feedback are generated by the evaluated method;
- the fixed operator is applied at runtime to those method-generated records;
- every application writes a replay pack that makes the generated noise
  inspectable and exactly replayable.

Consequently, RSEBench does **not** define one universal model-output file as
the N3 or N4 dataset. Such a file would only be valid for the model and method
that produced it. A release may include reference replay packs, but conformance
is determined by the fixed runtime specification and protected invariants.

## Stable boundaries

The public Python interface is exported from `rsebench.evidence`.

```python
from rsebench.evidence import EvidenceNoiseHook, HookContext

hook = EvidenceNoiseHook.from_spec_files(
    adapter=MyBaselineAdapter(),
    spec_paths=[n3_spec_path, n4_spec_path],
)

# Boundary N3: after the environment/verifier produced the rollout and reward,
# before reflection, diagnosis, or skill induction reads the trajectory.
learning_trajectory = hook.after_rollout(native_trajectory, context)

# Boundary N4: after the method produced critique/fault attribution,
# before revision, optimization, or skill-bank update consumes it.
learning_feedback = hook.after_feedback(
    native_feedback,
    native_trajectory,
    context,
)
```

The same configured hook may be installed in both arms. When
`HookContext.arm == "clean"`, both calls return the exact native object without
normalization; the implementation also rejects a spec whose benchmark or
domain differs from the runtime context. This identity path prevents the
benchmark adapter from silently changing a baseline's clean behavior.

## Adapter obligations

A method integration implements the `EvidenceAdapter` protocol:

1. `normalize_trajectory` maps the native rollout to a `TrajectoryRecord` with
   stable event IDs, event kinds, actions/observations, resource references,
   domain tags, reward, and success.
2. `denormalize_trajectory` maps the mutated N3 record back to the native type.
3. `normalize_feedback` maps reflection or fault attribution to a
   `FeedbackRecord` containing blamed event/resource IDs, diagnosis,
   recommendation, and scalar reward.
4. `denormalize_feedback` maps the mutated N4 record back to the native type.

An adapter must preserve the following invariants:

- N3: task identity, benchmark/environment state, scalar reward, and success;
- N4: the complete trajectory and scalar reward;
- clean arm: native object identity;
- noisy arm: only fields authorized by the selected operator may change.

Core-1 currently provides reference adapters for SkillOpt, SkillLearnBench, and
SkillAdaptor. New methods can reuse the public normalized records without
copying those baseline-specific implementations.

## Fixed specification

Each file under `benchmark/core1/runtime/<benchmark>/<N3|N4>.json` validates as
`RuntimeNoiseSpec` and fixes:

- stage and operator name;
- benchmark and domain;
- deterministic seed;
- selector and selector parameters;
- mutation budget (Core-1 uses exactly one mutation);
- protected fields;
- `record_inapplicable` failure policy;
- operator version.

Selection is deterministic over stable event/resource IDs. If the evaluated
method did not produce an eligible target, the hook records
`applicable=false`; it never substitutes another noise type. Applicability is
therefore a reported benchmark metric rather than a hidden fallback.

## Runtime outputs

For every configured call the hook writes:

```text
<run_dir>/mutation_audit/<arm>/<task_id>/<N3|N4>/
  input.json
  output.json
  audit.json
```

`audit.json` contains canonical input/output hashes, selected IDs, the exact
changed fragments, applicability, reason, selector, seed, and spec version.
These three files are the generated N3/N4 datum for that method/task/run.

The frozen split is also portable across machines: artifact locators use the
`rsebench-data://`, `rsebench-methods://`, or `rsebench-project://` schemes.
Reference runners resolve them only at execution time. Task hashes exclude
machine-specific locator strings and include artifact content hashes, so a
checkout path change cannot change benchmark identity.

## Benchmark conformance checks

A future method is conformant when its adapter passes all of the following:

1. clean-arm identity tests;
2. normalized-record schema validation;
3. N3 reward/success preservation;
4. N4 scalar-reward and trajectory preservation;
5. deterministic replay with the same task, spec, and seed;
6. replay-pack hash verification;
7. explicit accounting of applicable and inapplicable tasks.

Evaluation must use the same seed tasks for clean and noisy evolution, then
score both evolved artifacts on the same untouched clean test split. N3/N4
never mutate test data or the external environment itself.

For low-cost operator screening, `PairedEvolutionRunner.run` also accepts an
optional exclusive `seed_score_interval`. A score outside that interval writes
`seed/calibration.json` and the token ledger, then stops before either evolution
arm. This is a validation-cost guard, not a benchmark rule and not a license to
filter the final released test set by model outcomes.
